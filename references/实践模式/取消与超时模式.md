# 取消与超时模式

来源：[本地]（未联网确证）· 用途：给每个执行单元一条可证明的终止路径。

## 四种终止路径（缺一即不合格）

正常完成 / 超时 / 主动取消 / 失败。每条路径都必须：释放资源、上报结果、状态自洽。

## 语言机制对照

| 语言 | 取消 | 超时 |
|---|---|---|
| Java | `Thread.interrupt`、`Future.cancel`、`stop_token`(虚拟线程) | `Future.get(t)`、`tryLock(t)` |
| Python | `asyncio.Task.cancel()` → `CancelledError` | `asyncio.wait_for`、`join(t)` |
| Go | `context.WithCancel/WithTimeout` 显式传递 | `ctx.Done()` + `select` |
| C++20 | `std::jthread` + `std::stop_token` | `wait_for` / `try_lock_for` |
| .NET | `CancellationToken` 全链传递 | `CancelAfter` / `Task.WhenAny(delay)` |

## 高频结论

1. **协作式**：取消是「请求」，工作必须在检查点响应；不可取消的阻塞调用要隔离到可丢弃执行器。
2. 吞掉取消 = 最严重错误：`InterruptedException` 须重设中断位或继续抛出；
   `except Exception` 不得捕获 `CancelledError`（Python 中它继承 `BaseException`）。
3. 超时值来自配置与 SLO，不来自魔法数；跨层调用 deadline 递减传播，避免「下游比上游久」。
4. 取消后的中间态要么回滚，要么可识别（幂等键/状态标记），禁止半发布对象。
5. 重试须有上限 + 退避 + 取消检查，否则取消信号被重试循环吞掉。
