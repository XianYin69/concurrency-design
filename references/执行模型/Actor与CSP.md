# Actor 模型与 CSP（Go）

来源：[本地]（未联网确证）· 用途：以「传递消息代替共享内存」消除数据竞争。

## 两种范式

| | Actor（Erlang/Akka） | CSP（Go） |
|---|---|---|
| 口号 | 每个 actor 私有状态 + 邮箱 | 「不要通过共享内存通信，要通信共享内存」 |
| 拓扑 | 动态、按名字/引用发消息 | 静态通道为一等值，多路复用 `select` |
| 失败 | supervisor 树重启（let it crash） | error 值显式传播，panic 局部恢复 |
| 背压 | 邮箱有界性须显式配置 | 通道缓冲大小即背压 |

## 高频结论

1. 串行化边界 = 单线程 owner：状态只由一个 actor/goroutine 拥有，外部经消息请求变更 →
   天然免锁（遗留改造首选，见 [共享可变状态约束](../../resistance/共享可变状态约束/共享可变状态约束.md)）。
2. 通道关闭规则：**发送方关闭、接收方判活**；重复关闭/向已关通道发送即 panic。
3. `select` 无默认分支会阻塞 → 须配 `default`（非阻塞）或超时分支（`time.After`）。
4. 消息须是不可变/所有权转移的数据；传指针等于共享内存，只是把竞态藏进信封。
5. 循环依赖的 actor/通道会形成等待环 —— 与锁序同构，仍须验环（`deadlock_check.py`）。

## 适用判据

- 状态可自然分区（会话、账户、玩家）→ Actor/CSP 优；需全局一致快照/大范围随机读 → 共享结构 + 锁更直接。
