# 死锁四条件与破坏策略

来源：[本地]（未联网确证）· 用途：设计阶段消除死锁，而非事后救火。

## 四个必要条件（同时成立才可能死锁）

1. **互斥**：资源同时只能被一个线程持有。
2. **持有并等待**：持锁的同时请求新锁。
3. **不可剥夺**：锁只能由持有者主动释放。
4. **循环等待**：存在线程/锁的等待环。

## 破坏手段（按工程性价比排序）

| 破坏 | 做法 | 代价 |
|---|---|---|
| 循环等待（首选） | **全局锁序**：给锁编号，所有路径按同一顺序获取 | 需书面约定 + 验环 |
| 持有并等待 | 一次性申请全部锁（`tryLock` 全有或全无）或预分配资源 | 吞吐下降 |
| 不可剥夺 | 超时后释放已持有锁并退避重试 | 需可回滚的临界区 |
| 互斥 | 改为无锁/不可变/消息传递 | 实现复杂 |

## 相关陷阱

- **活锁**：都在退避且节奏一致 → 退避须随机化（jitter）。
- **饥饿**：非公平锁 + 高争用 → 需公平性或限流。
- **锁内阻塞 IO / 回调**：把死锁变成级联超时（见 [锁粒度约束](../../resistance/锁粒度约束/锁粒度约束.md)）。
- **线程池自死锁**：任务提交任务并等待结果，池满即锁死 → 分层池或禁止内联等待。
- 数据库/分布式锁：等待图在引擎侧，须看 `40P01` 类错误与重试语义。

## 检测

- 静态验环：`python -B scripts/deadlock_check.py <加锁顺序日志>`（环数必须为 0）。
- 运行时：Java `ThreadMXBean.findDeadlockedThreads`、jstack、Python faulthandler、
  Go `runtime` dump；TSan 亦报锁序问题。
