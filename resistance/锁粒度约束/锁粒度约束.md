# 锁粒度约束（锁序无环 · 临界区最小 · 持锁时长有界）

本约束规定同步结构的设计门槛。任一条不满足即**不得合入**，改走兜底。

## 必须

1. **全局锁序**：多把锁的获取顺序须有书面约定（编号/层级表），所有路径同序；
   用 `deadlock_check.py` 对加锁顺序日志验环，环数必须为 0。
2. **临界区最小**：只包住真正的不变量破坏窗口；禁止整方法一把大锁、禁止锁内循环重活。
3. **持锁时长有界**：锁内禁止阻塞 IO（网络/磁盘/等待他人）、禁止 sleep、禁止调用未知耗时的回调；
   确需时改为「锁内取数据 → 锁外做慢活 → 锁内合并」。
4. **锁与数据同生命周期**：锁保护的字段成组声明，命名体现归属（`_x guarded by self._lock`）。
5. 读写分离：读多写少用读写锁/快照/无锁读，须给出比例证据（压测数据）而非直觉。
6. 分层加锁：粗粒度正确性优先，性能优化须经 [取消安全约束](../取消安全约束/取消安全约束.md)
   与压测复验；细化锁（分段/条带/无锁）须逐条重证锁序无环。
7. 有超时与失败路径：`tryLock`/`lock_for` 类接口须设超时并定义拿不到锁时的行为（退避/降级/报错）。

## 禁止

- 在持有锁 A 时等待外部输入（用户、下游服务、队列）再取锁 B。
- 用嵌套锁「先都加上」保平安；锁数量与深度须有论证。
- 在构造函数/析构函数中调用可重入的公开加锁方法（this 逃逸）。
- 以「压测没死锁」替代锁序证明——死锁是概率事件，须静态验环。
- 用全局单一大锁换取「简单」却不声明代价；粗锁也须写明吞吐上界与验证方式。

## 兜底

- 锁序冲突无法立刻消除：引入**锁层级 + 单向依赖**（只允许高层调低层），或改为消息传递串行化。
- 必须锁内做慢操作：改为两阶段（快照 + 提交），并在逻辑链记录取舍与被否方案。
- 无法验环（动态反射取锁）：降级为「只出方案不出代码」，向用户明示未证明的风险。

## 违规后果

- 锁序有环 → 死锁挂起，生产表现为吞吐归零且难以复现。
- 锁内阻塞 IO → 线程池饥饿、级联超时、雪崩。
