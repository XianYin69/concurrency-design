# 取消安全约束（超时 · 取消传播 · 幂等收尾）

本约束规定任何并发执行单元（线程/任务/协程/actor）的生命周期门槛。

## 必须

1. **每个执行单元都有终止路径**：正常完成、超时、取消、失败四条，缺一即不合格。
2. **超时上限显式**：任何等待（join/条件变量/队列取/锁获取/远程调用）须有超时；
   禁止无限等待。压测与生产默认值须写入配置而非硬编码魔法数。
3. **取消可传播**：取消信号沿调用树向下传递（Java `interrupt` / Python `asyncio.CancelledError` /
   Go `context` / C++ `stop_token`）；顶层取消必须能终止叶子工作。
4. **取消点可检查**：长循环与阻塞调用处须检查取消/超时，不得只在入口出口检查。
5. **收尾幂等**：资源释放（连接、文件、锁、临时数据、注册表项）在任一终止路径都执行且不重复生效；
   用 `try/finally`、`using`、`defer`、结构化并发的作用域保证。
6. **失败不外溢为静默**：子任务异常须被收集并上报（`Future` 检查、gather 的 return_exceptions、
   supervisor 策略），禁止「线程死了没人知道」。
7. 取消后状态自洽：半途而废的工作须回滚或标记为可识别的中间态，不得留下脏数据/半发布对象。

## 禁止

- 只靠 daemon 线程/后台任务「进程退出就算清理」掩盖缺失的终止路径。
- 捕获取消异常后吞掉不再传播（Java 吞 `InterruptedException` 不重设中断位；
  Python 吞 `CancelledError` 不 re-raise）。
- 用 `Thread.stop`/强杀/取消不可安全取消的阻塞调用当作「快速失败」。
- 无界重试：重试须有上限、退避与取消检查（与背压限流联动）。
- 取消与业务失败混为同一异常类型，导致上层无法区分处理。

## 兜底

- 第三方阻塞调用不可取消：放入**可丢弃的执行器**并设硬超时 + 隔离进程/线程池，
  记逻辑链与中断，向用户明示残留风险。
- 无法引入取消机制（遗留 API）：改为「短任务切片 + 协作式标志位轮询」，并给出轮询开销证据。
- 压测超时：`stress_test_runner.py` 到点即停并出剖面，禁止无限挂起等待。

## 违规后果

- 无终止路径 → 关停挂死、部署卡住、资源泄漏。
- 取消被吞 → 上层以为已停而工作仍在跑，重复副作用与数据损坏。
